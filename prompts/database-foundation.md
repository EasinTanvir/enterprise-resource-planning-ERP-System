# ERP Database Foundation Implementation Prompt

## Goal

Initialize the complete, migration-managed PostgreSQL database foundation for the multi-tenant physical-retail ERP inside `server/`, using Drizzle ORM and the existing Neon `DATABASE_URL` environment variable. The database design must support all defined ERP domains, preserve referential integrity and financial/inventory history, and make PostgreSQL Row-Level Security (RLS) an enforceable tenant-isolation boundary from the first migration.

## Skills Read

- `AGENTS.md`
- `.agents/skills/neon-postgres/SKILL.md`

The Neon skill requires Drizzle-managed schema and migrations, pooled application traffic where appropriate, and a direct (non-`-pooler`) connection for migration operations. Schema changes must never be applied ad hoc.

## Existing Code Inspected

- `server/package.json`: NestJS 11 and `@nestjs/config` are installed; Drizzle, Drizzle Kit, and a PostgreSQL driver are not yet installed.
- `server/src/app.module.ts`: loads configuration and the placeholder authentication module only.
- `server/src/authentication/*`: authentication is currently an empty scaffold; no trusted user or tenant context exists yet.
- `server/.env`: contains `PORT` and an existing `DATABASE_URL`; its value was not read or exposed.
- No current Drizzle config, schema, migrations, or database module exists.

## Product Context

The product is a multi-tenant SaaS ERP for physical retail only. It includes platform users, tenants with one-time lifetime licenses, tenant users/RBAC, customers, catalog, inventory, suppliers, purchases, sales, returns, invoices, payments, reports, notifications, audit logs, and tenant settings. Do not add ecommerce, subscriptions, accounting, or unrelated tables.

## Architecture Decisions

- Keep all database assets in the NestJS backend: `server/src/database/` for Drizzle connection/schema exports and `server/drizzle/` for generated SQL migrations and migration metadata.
- Use `drizzle-orm`, `drizzle-kit`, and `pg` with a reusable `pg.Pool` in a NestJS database module. Application query traffic uses `DATABASE_URL`.
- Add `DATABASE_URL_UNPOOLED` as the preferred migration-only environment variable. Drizzle Kit reads it first and falls back to `DATABASE_URL` only for a local direct URL; documentation must state that Neon migrations require the direct hostname (without `-pooler`). Do not replace or disclose the existing `DATABASE_URL`.
- Use the PostgreSQL `pgcrypto` extension and UUID primary keys generated by `gen_random_uuid()`.
- Standardize timestamps as `timestamptz` (`created_at`, `updated_at` where mutable) and money/quantities as fixed precision numeric columns, never floats.
- Use `public` for the ERP schema initially. Organize Drizzle table definitions by domain and export a single schema barrel for migrations and typed application access.
- Model platform and tenant users separately only when needed by the access model: `users` is a platform identity table, while `tenant_memberships` carries tenant membership, role assignment, status, and tenant-specific attributes. A user may be a platform super-admin and/or a tenant member.
- RLS policy evaluation receives tenant context only from trusted backend authentication. The database never trusts a request body tenant ID.

## Database Design

### Identity, tenancy, licenses, and RBAC

- `users`: account identity, unique normalized email, password hash, display fields, platform role/state, timestamps.
- `tenants`: tenant name, unique slug, active/suspended status, business metadata, timestamps.
- `tenant_licenses`: one current lifetime license per tenant; active/suspended/revoked status, activation/revocation metadata. No recurring billing fields.
- `tenant_memberships`: tenant/user relation, tenant-scoped status, employee code, timestamps, unique `(tenant_id, user_id)`.
- `roles`: tenant-scoped custom roles plus protected system-role records; unique role names per tenant.
- `permissions`: platform-owned permission catalogue with unique permission key.
- `role_permissions`: role-to-permission mapping.
- `membership_roles`: membership-to-role mapping, supporting future multi-role assignment.

### Tenant master data

- `categories`: tenant-scoped name, optional parent category, description, active status; unique name per tenant where appropriate.
- `products`: tenant-scoped SKU, category, name, description, unit, purchase/selling prices, reorder level, image reference, status; unique `(tenant_id, sku)`.
- `customers`: tenant-scoped contact data, optional customer code, status, timestamps; use tenant-aware unique indexes only for intended identifiers, not nullable contact information.
- `suppliers`: tenant-scoped business/contact data, optional supplier code, status, timestamps.
- `company_settings`: one settings record per tenant, including business contact data, currency, invoice prefix/footer, tax configuration, and timestamps.

### Inventory

- `inventory_balances`: one row per `(tenant_id, product_id)` with on-hand, reserved, and available quantities, constrained to non-negative values for the initial no-negative-inventory policy.
- `stock_movements`: immutable, tenant-scoped inventory ledger with product, signed quantity, movement type (`purchase`, `sale`, `return`, `adjustment`, `damage`, `opening_balance`), optional source reference, reason, actor, created timestamp. Add indexes for tenant/product/date and tenant/type/date reporting.
- Inventory balances are changed only through future transactional inventory service operations that create matching stock movements; no database consumer may silently update balances.

### Purchasing

- `purchases`: tenant, supplier, purchase number (unique per tenant), status (`draft`, `confirmed`, `partially_received`, `received`, `cancelled`), monetary totals, dates, actor/notes, timestamps.
- `purchase_items`: purchase/product lines, ordered and received quantities, immutable captured unit cost, discount/tax, line total.
- Inventory receipt occurs only in a future receive-purchase transaction; drafts and confirmations never add stock.

### Sales, invoicing, and payments

- `sales`: tenant, customer, sale number (unique per tenant), status (`draft`, `confirmed`, `cancelled`), captured totals, confirmed/cancelled metadata, creator, timestamps.
- `sale_items`: sale/product lines with immutable captured SKU/name/unit price, quantity, discount/tax, line totals.
- `invoices`: tenant, sale, invoice number (unique per tenant), status, issue/due dates, totals and payment status; one invoice per sale initially.
- `payments`: tenant, invoice and/or sale references constrained so they remain in the same tenant, method (`cash`, `card`, `bank_transfer`, `mobile_banking`, `other`), status, amount, paid-at date, provider reference, notes, recorder, timestamps. Supports partial payments.

### Sales returns, operational records, and settings

- `sales_returns`: tenant, original sale, return number (unique per tenant), customer, status (`pending`, `approved`, `rejected`, `refunded`), reason, financial totals, approver metadata, timestamps.
- `sales_return_items`: returned sale item/product, quantity, captured refund amount, condition/reason.
- `notifications`: tenant-scoped recipient, type, title/body, read state, related resource, timestamps.
- `audit_logs`: append-oriented tenant-scoped audit data with actor, action, resource type/id, safe JSON metadata, timestamp. Do not store credentials, access tokens, or password hashes.

### Integrity, constraints, and indexes

- All tenant-owned tables include a non-null `tenant_id` foreign key to `tenants` and indexes beginning with `tenant_id` for their expected query paths.
- Use composite foreign keys or database triggers where necessary to prevent cross-tenant relationships (for example, a tenant sale referencing another tenant’s customer/product). Prefer composite unique keys such as `(tenant_id, id)` on tenant-owned parents, then composite child foreign keys referencing `(tenant_id, parent_id)`.
- Add check constraints for valid positive quantities, non-negative monetary values, state-compatible timestamps, and valid inventory deltas. Preserve historical transactions through statuses and compensating records, not destructive cascading deletes.
- Use restrictive foreign-key deletion behavior for financial/inventory records and safe `set null` behavior only for optional actor references.

## RLS and Tenant Context Requirements

- Enable and force RLS on every tenant-owned table, including join and activity tables such as `tenant_memberships`, role assignments, inventory, and audit logs.
- Create a dedicated non-owner application role for runtime access. Do not run normal API queries as the migration/schema owner, because table owners can bypass RLS.
- Provide an idempotent migration to create the application role only when permitted by the deployment credentials; otherwise document the required Neon SQL setup separately and fail clearly rather than pretending RLS is enforced.
- RLS policies must derive the tenant from `current_setting('app.current_tenant_id', true)::uuid`, with `missing_ok` handling that denies access by default. Policies must apply `USING` and `WITH CHECK` to protect reads and writes.
- Do not create permissive policies based on a client tenant ID. The future NestJS auth guard must resolve tenant membership, then execute `SELECT set_config('app.current_tenant_id', $tenantId, true)` inside the same transaction/client scope as every tenant query. Pooled connections must never depend on a session-persistent `SET`.
- Platform-level super-admin operations must use a deliberately separate, reviewed privileged path; they must not accidentally bypass tenant RLS in ordinary tenant APIs.
- Include migration tests/verification SQL demonstrating: no tenant context returns no rows; Tenant A cannot select/update/delete/insert Tenant B records; and valid Tenant A context can access only its own data.

## Drizzle and Migration Setup

- Add `drizzle.config.ts` under `server/`, pointing to the schema barrel and `server/drizzle/` output.
- Add package scripts for schema generation, migration application, and Drizzle Studio with clear names (for example `db:generate`, `db:migrate`, and `db:studio`). Use the direct URL for migrations.
- Add a `DatabaseModule`, connection provider, typed Drizzle database export, lifecycle cleanup for the pool, and a tenant transaction helper that scopes `set_config` correctly. Do not implement domain repositories, controllers, or authentication flows in this database-foundation change.
- Generate the initial Drizzle migration from the schema; do not use `drizzle-kit push` as the production schema workflow.
- Update `server/.env.example` (not the existing secret-containing `.env`) with `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, and `PORT` placeholders, plus non-secret comments explaining pooled/direct usage.
- Update `server/README.md` with dependency setup, Neon connection guidance, migration commands, rollback/branch testing guidance, and the RLS runtime contract.

## Acceptance Criteria

- Drizzle can generate an initial migration from source-controlled TypeScript schema definitions.
- Every product-scope business table has tenant ownership, tenant-aware foreign keys/indexes, and RLS enabled/forced.
- Database operations with no tenant context default to denial; policies prevent cross-tenant reads and writes.
- The design supports complete physical-retail purchasing, inventory, sales, returns, invoice, partial-payment, licensing, RBAC, settings, notification, and audit workflows without e-commerce or recurring-billing concepts.
- Monetary/quantity types, uniqueness constraints, foreign keys, and lifecycle statuses preserve business integrity and auditability.
- Backend runtime connections are pooled/reusable, while migrations are documented and configured to use a direct Neon connection.
- No database secret is committed or printed.

## Manual Testing Steps

1. Create a Neon development branch and set its direct connection string as `DATABASE_URL_UNPOOLED`; retain the pooled URL as `DATABASE_URL` for app traffic.
2. Run the generated migration on the development branch.
3. Create two tenant records and representative customer/product records for each using a controlled setup path.
4. Connect as the application role with no `app.current_tenant_id`; verify tenant-owned queries are denied or return no rows.
5. In a single transaction set Tenant A context through the supplied backend helper; verify only Tenant A records are visible and writable.
6. Attempt to access, update, or insert a Tenant B relation while Tenant A context is set; verify PostgreSQL RLS/FKs reject it.
7. Confirm that creating a purchase draft changes no inventory, while the future receiving transaction contract requires a stock movement and inventory update together.
8. Confirm that the existing `server/.env` remains unchanged and untracked.
